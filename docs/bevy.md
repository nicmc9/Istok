# Почему не Bevy

Заметка для разговоров «почему бы не взять сразу Bevy». Обновлять, когда меняется Istok или сам Bevy.
Сверка с кодом — **2026-11-17**. Архитектура кадра — в [acrhitecture.md](acrhitecture.md), решения D2 и D7 — в [task.md](task.md).

Короткий ответ: из Bevy уже взято то, что стоит брать как библиотеку. Свой движок нужен из-за кадра и границ, которые Bevy не отдаёт.

В Istok стоят `bevy_ecs`, `bevy_reflect` и `bevy_tasks` (см. [crates.md](crates.md)). Игровой код пишет системы, компоненты и рефлексию так же, как в Bevy, только импортирует их через `engine::ecs`. Вопрос не в том, писать ли свой ECS. Вопрос в том, чьим будет всё остальное: окно, кадр, рендер, ресурсы, физика и звук.

## Что у каждого своё

| | Istok | Bevy |
|---|---|---|
| ECS, рефлексия, пул задач | Библиотеки Bevy за своим фасадом | Они и есть ядро |
| Кадр | Логика на фиксированном шаге, рендер с частотой экрана. Состояние кадра идёт тройным буфером, команды — очередью. Поток рендера владеет `wgpu` и никого не ждёт | Игра — это расписание систем. Рендер может идти параллельно со следующим кадром, но мир рендера, extract и ресурсы — часть Bevy |
| Платформы | macOS, Linux, Android, iOS, Web с первой итерации. На Web только WebGPU, на GL только GLES 3.2 | Те же платформы плюс Windows и запасной WebGL2, потому что движок обслуживает всех |
| Физика и звук | За трейтами, в бинарник не попадают, пока проект не включил feature и CVar | Физики в самом движке нет. Звук и рендер — часть движка, а не сменный бэкенд |
| Сеть | Загрузчик контента: повторы, докачка, дисковый кеш, SHA-256. Мультиплеера нет | Сеть игры — отдельные плагины сообщества |
| Редактор | После того как обкатается движок. Сцены в RON уже есть | Свой редактор ещё ранний, зато вокруг движка больше готовых плагинов и примеров |
| Зрелость | Первое поколение: PBR, 2D, клипы анимации, текст, частицы на CPU, постэффекты, консоль и CVar | Годы функций, которых здесь ещё нет: граф анимаций, UI игры, GPU-driven рендер, запечённый свет |

Bevy тоже умеет фиксированный шаг и параллельный рендер. Разница в договоре. В Istok главный поток никогда не трогает устройство GPU, снимок кадра можно потерять, команду нельзя, а при сворачивании на Android и iOS главный поток ждёт, пока рендер отпустит surface. Это записано как архитектура, а не как поведение плагина.

## Когда Bevy — правильный выбор

Если цель — игра, а не движок, Bevy честнее. Там уже есть примеры, плагины и люди, которые чинят рендер. Свой движок на этом месте — это годы работы, которые не видны игроку. Istok как раз в этой точке: редактора нет, графа анимаций нет, частицы считает CPU.

## Когда свой движок оправдан

Команда пришла из C++ и хочет движок с тем же устройством, к которому привыкла: слои, CVar, кадр с фиксированным шагом, GPU в отдельном потоке, физика и звук за фасадом. В Bevy это нельзя поставить плагином. Рендер, цикл и ресурсы там — сам движок. Форк этой части расходится с каждым релизом Bevy, а плагины сообщества рассчитаны на их расписание, а не на наше.

Istok сужает матрицу специально. Нет Windows, нет WebGL2, нет запасного GLES 3.0, нет мультиплеера. Bevy такое сужение не сделает: ему нужно оставаться движком для всех.

Одной фразой: Bevy — готовая игра поверх их расписания. Istok — кадр и границы, которые команда может менять целиком, оставив себе только ECS Bevy.
